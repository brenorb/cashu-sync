Cashu Sync · Lesson 1

The repo is a concurrency protocol around a Cashu wallet.

The key to this codebase is knowing which system owns which truth. Once that is clear, the NIPs, NUTs, journal, and privacy claims line up.

One sentence: paired PWAs share full spending authority; they synchronize a complete encrypted snapshot through a custom Nostr relay, while Nutshell remains the authority for whether money moved.

1. The three truths

SystemWhat it ownsWhere to read it
WalletPlaintext seed/proofs, exact requests, counters, local journal, validation, and applying snapshots.localWalletRepository.ts
NutshellQuotes and mint-side proof state. The wallet may be stale; the mint decides whether a proof is spent or a quote paid.cashuOperationGateway.ts
RelayOnly the current signed encrypted event head, using SQLite compare-and-swap.store.go

That split is deliberate. The relay is a sequencer and encrypted mailbox, not a distributed transaction coordinator. There is no atomic “relay write + mint write”; safety comes from durable intent, ordering, exact replay, and reconciliation.

2. What actually syncs

The snapshot is not a dump of IndexedDB. The typed v0 schema carries only what another authorized wallet needs to reconstruct the wallet projection:

revision · previous_event_id · mint · unit proofs · NUT-13 counters · quotes · accounting history pending_operation (null | exactly one mint/melt journal)

Each snapshot becomes a signed Nostr event:

kind: 30078 tags: d=com.silentlink.cashu-sync.wallet.v0, prev=<head>, schema=0 content: NIP-44 v2 ciphertext(snapshot) pubkey + id + sig: dedicated sync key

NIP-78 supplies the app-data envelope shape for kind 30078; NIP-01 supplies event identity/signatures. The repo's prev check is the important custom layer.

3. Why ordinary Nostr replacement was not enough

With ordinary addressable-event replacement, two stale wallets can both publish and silently overwrite one another. Cashu proofs are bearer-like state: silently dropping a newly issued proof from the shared projection is unacceptable.

The relay therefore performs this transaction for one (pubkey, d) stream:

duplicate event? → idempotent success read current head require incoming prev == current head insert immutable event → advance head → commit otherwise: conflict, store nothing, broadcast nothing

On the client side, syncCoordinator.ts serializes local calls, verifies signatures and decryption, rejects rollback/branch/gap, and applies a valid snapshot in one Dexie transaction. The open relay subscription is a prompt; startup, foreground, pre-operation, and reconnect pulls are the correctness path.

4. The operation safety boundary

Mint and melt are not allowed to start from “I think my local state is current.” They start from a current relay head and a durable pending operation.

pull + reconcile old pending → prepare exact Cashu request → persist pending journal locally → publish pending snapshot; wait for CAS OK → mark submitted durably → submit exact request to Nutshell → persist response/change → publish final snapshot; clear journal

Read syncOperationCoordinator.ts beside operationJournalRepository.ts. The key failure rule is easy to test: a stale or rejected prepared publish causes zero state-changing mint/melt calls. After submission, errors become “unknown,” not “failed”; the journal survives until reconciliation resolves them.

For a melt, selected inputs are reserved first, change is made durable, and only then are paid inputs removed. For a mint, the exact blinded outputs are persisted before submission; NUT-09 can restore signatures for those exact outputs if the response was lost.

6. Privacy: what is guaranteed, what is not

Strong guarantees, assuming the client and deployment are not compromised

  • The relay stores ciphertext and cannot calculate the balance, read proofs, or decrypt the seed.
  • Event signatures, inner/outer predecessor agreement, revision checks, and atomic local apply reject tampering and rollback before state is accepted.
  • The mint sees the proof-bearing requests it must see; the relay does not see those plaintext requests.
  • Every paired wallet is intentionally equal-authority; there is no hidden server-side copy with more power.

Hard limits

  • A paired device has the mnemonic and sync secret, so it can spend everything. There is no v0 revocation.
  • The shared sync pubkey makes one wallet's event stream linkable. NIP-44 hides content, not metadata.
  • The relay can deny service, delete history, or withhold the head. It cannot make a valid old snapshot look new, but it can block recovery until restored.
  • The current one-scan UI encodes the encrypted authority bundle and its temporary passphrase in the same URL payload. No plaintext mnemonic appears, but possession of the full URL is possession of the handoff.
  • The inherited browser base still has plaintext mnemonic/localStorage exposure called out by wallet-base.md.

7. What I would improve first

  1. Pairing URL: remove authority from URLs; wire the existing ephemeral two-QR protocol or use an authenticated out-of-band exchange, then scrub route state immediately.
  2. Browser secrets: replace plaintext mnemonic storage and review logs, service workers, clipboard, crash reports, and backups as one secret-handling surface.
  3. Deployment: add an operator enrollment flow, controlled PWA updates around operations, backup/restore drills, monitoring, and an independent audit.
  4. Scalability/privacy: only after v0 hardening, explore per-device keys/revocation, multiple relays, batching/delays, or the deferred event-sourced multiwriter model.

Retrieval check

Answer these without looking back, then open the answer:

  1. Which system decides whether a proof is spent?
  2. Why does the relay require prev to equal its current head?
  3. What must be durable before the first state-changing mint/melt request?
  4. Why is a timeout after submission not safe to treat as failure?
  5. What does the current quick-pair URL protect, and what does it still expose?
Answer key

Nutshell decides proof state. prev turns a last-write-wins stream into a conditional write, preventing stale children from silently replacing the head. The exact prepared request and pending journal snapshot must be durable and CAS-accepted. A request may have reached the mint even if the response was lost, so the wallet must reconcile rather than retry blindly. The URL hides plaintext authority from casual inspection, but the encrypted payload and its passphrase travel together, making the full URL a bearer secret.
